# 14 — Bcrypt

> The specific algorithm we use to hash passwords. Read [15 — Password Hashing](15-Password-Hashing.md)
> first for the *why* (salting, work factors, timing). This chapter is the *how*: bcrypt's anatomy,
> cost factor, the 72-byte limit, and real measurements from this project.

---

## Definition & history

**bcrypt** is a password-hashing function designed by **Niels Provos and David Mazières in 1999**,
based on the **Blowfish** cipher. It was built specifically to be **slow and adaptive** — the opposite
of general-purpose hashes like MD5/SHA, which are designed to be fast. Its key innovation: a tunable
**cost factor** that can be raised over the years as computers get faster, so bcrypt stays expensive
to brute-force decades later. It remains a solid, widely deployed choice today.

---

## Anatomy of a bcrypt hash

bcrypt's output is a single self-contained string that encodes everything needed to verify a password
later — no separate salt or cost columns:

```
  $2b$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW
  │  │  │ └──────────────────────┬───────────────────────────┘
  │  │  │                        └ 22-char salt + 31-char hash (Base64-ish)
  │  │  └ cost factor: 12  (2^12 = 4096 key-expansion rounds)
  │  └ algorithm version: 2b  (the modern, correct variant)
  └ marker
```

A real hash from this project: `$2b$12$4geBu7uR415mEBxmM.XiJ.zCXG0CVUdyMhslo47Q4QaVZsPzNBJLa` — always
exactly **60 characters**. Because the salt and cost live *inside* the string, `verifyPassword` needs
only the stored value to re-derive and compare.

---

## The cost factor (work factor)

The cost is a **base-2 exponent**: work ∝ 2^cost. Each +1 **doubles** the time to hash — for a
legitimate login *and* for an attacker's every guess.

### Real measurements (this project's hardware, pure-JS bcryptjs)

| cost | median ms/hash | logins/sec | note |
|-----:|---------------:|-----------:|------|
| 8  | ~30 ms   | ~34 | too fast — weak |
| 10 | ~80 ms   | ~12 | OWASP floor |
| 11 | ~145 ms  | ~7  | snappy |
| **12** | **~600 ms** | ~1.7 | **our default** |
| 13 | ~1180 ms | ~0.8 | slow |
| 14 | ~1880 ms | ~0.5 | painful |

*(Generated by `scratchpad/bcrypt-bench.js`. Native `bcrypt` would be faster than these pure-JS
numbers, so treat them as conservative.)*

### Choosing the number

The target: **the highest cost that still feels instant to a user** — commonly **~250–500 ms** per
hash. On *this* machine, cost 12 measured ~600 ms (a touch high because bcryptjs is pure-JS and this
CPU is modest); 11 (~145 ms) would also be defensible. We keep **12** as the default (a widely
recommended value and comfortably above the cost-10 floor) but made it **configurable** via
`BCRYPT_COST` so it can be tuned per environment — *measure on your production hardware and adjust.*
Bounds are enforced to `[10, 15]` in config (fail-fast outside that).

> Why "highest tolerable"? Login happens rarely per user, so ~half a second is fine for them — but it
> makes an attacker's billions of guesses astronomically expensive. Asymmetric cost is the whole game.

---

## The 72-byte limit (a real footgun)

bcrypt only processes the **first 72 bytes** of input; anything beyond is silently ignored. Two
consequences:

1. Very long passwords are effectively truncated — `"…72 bytes…AAAA"` and `"…72 bytes…BBBB"` verify
   the same. We cap password length at 72 in the validator (docs 21) so behavior is explicit, and it
   also blunts a **slow-hash DoS** (submitting huge strings to waste CPU).
2. Bytes ≠ characters: multi-byte UTF-8 (emoji, accents) consume the budget faster. 72 bytes may be
   far fewer than 72 characters.

A known historical wrinkle: some bcrypt implementations mishandle **null bytes** within the password;
the `$2b$` version we use is the corrected variant. (argon2 has no such length quirk — see below.)

---

## How our code uses it (`src/utils/password.ts`)

- `hashPassword(plain)` → `genSalt(config.security.bcryptCostFactor)` then `hash`. The salt encodes the
  cost; a random salt per call means the same password hashes differently every time (verified in
  tests).
- `verifyPassword(plain, hash)` → `bcrypt.compare`, which re-derives using the embedded cost+salt and
  compares in **constant time** (timing-attack safe, docs 15).
- `passwordNeedsRehash(hash)` → parses the cost out of the `$2b$<cost>$…` string; returns true if it's
  below the configured cost, so login can transparently upgrade it (Phase 6).
- `BCRYPT_MAX_PASSWORD_BYTES = 72` documents the limit for the validator/tests.

We use **bcryptjs** (pure-JS) rather than native **bcrypt** to avoid native compilation on Windows/
Render; identical `$2b$` hashes, slightly slower (hence conservative timings).

## bcrypt vs the alternatives

- **argon2 (argon2id)** — winner of the 2015 Password Hashing Competition; **memory-hard** (resists
  GPU/ASIC attacks better than bcrypt) and the modern first choice when available. No 72-byte limit.
  We'd reach for `argon2` in a greenfield high-security system; bcrypt is chosen here for its ubiquity,
  simplicity, and zero-native-build story — and it's still perfectly acceptable.
- **scrypt** — also memory-hard; solid, a bit fiddlier to tune.
- **PBKDF2** — FIPS-approved and widely available, but *not* memory-hard (weaker vs GPUs); acceptable
  where compliance requires it.
- **MD5 / SHA-1 / SHA-256** — **never** for passwords: fast, no work factor.

---

## Common mistakes

- **Treating cost as linear** — it's exponential; +1 doubles the work.
- **Copying a cost factor blindly** without measuring on your hardware.
- **Ignoring the 72-byte limit** — silent truncation; cap length in validation.
- **Pre-hashing with a fast hash to dodge the 72-byte limit** (e.g. `bcrypt(sha256(pw))`) — a subtle
  pattern with pitfalls (null bytes, Base64 expansion); prefer argon2 if long inputs matter.
- **Using an old `$2a$`/`$2y$` lib with the null-byte bug** — use a maintained `$2b$` implementation.
- **Setting cost so high logins take seconds** — hurts UX and becomes its own DoS vector.

---

## Best practices

- Pick the **highest cost with acceptable latency** (~250–500 ms); **measure**, and make it
  **configurable** (we use `BCRYPT_COST`, bounded `[10,15]`).
- Let bcrypt **generate and embed the salt**; store just the 60-char string.
- **Cap password length** to 72 bytes in validation.
- **Rehash on login** to raise the cost over time (docs 15).
- Consider **argon2id** for new, high-security systems.

---

## Interview questions

1. **What makes bcrypt suitable for passwords when SHA-256 isn't?** A tunable, deliberately slow work
   factor plus built-in salting; SHA-256 is fast and unsalted by default.
2. **What's encoded in a bcrypt hash string?** Version, cost factor, salt, and hash — all in ~60 chars.
3. **What does the cost factor do, and how does +1 affect it?** Sets rounds = 2^cost; +1 doubles the
   work.
4. **What is bcrypt's 72-byte limit and why does it matter?** Input beyond 72 bytes is ignored → cap
   length; watch multi-byte characters.
5. **bcrypt vs argon2?** argon2id is memory-hard (better vs GPUs) and has no length limit; bcrypt is
   ubiquitous, simple, and still solid.
6. **How do you pick the cost factor?** Measure on real hardware; choose the highest value keeping a
   login hash around 250–500 ms; revisit as hardware improves.

## Summary

- **bcrypt** (1999, Blowfish-based) is a **salted, adaptive** password hash; output is a 60-char
  `$2b$<cost>$<salt+hash>` string.
- The **cost factor** is exponential (2^cost); pick the **highest tolerable** (~250–500 ms) and make it
  **configurable** — our default is **12** (`BCRYPT_COST`, bounded `[10,15]`), measured at ~600 ms here.
- Mind the **72-byte** input limit (we cap length in validation).
- **argon2id** is the modern alternative; bcrypt remains a strong, pragmatic choice.
